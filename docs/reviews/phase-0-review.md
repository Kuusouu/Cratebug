## Reproduced commands

The documented workflow was reproduced from a disposable clean checkout:

```powershell
mise install
mise exec -c "go install github.com/wailsapp/wails/v2/cmd/wails@v2.13.0"
$env:Path = "$(mise exec -c "go env GOPATH")\bin;$env:Path"

Push-Location frontend
mise exec -c "bun install --frozen-lockfile"
Pop-Location

mise exec -c "go version"
mise exec -c "bun --version"
mise exec -c "wails version"

.\check.ps1
mise exec -c "wails build -clean -platform windows/amd64 -nopackage -nocolour"
mise exec -c "wails build -clean -platform windows/amd64 -nsis -installscope user -nocolour"
```

**Result:** Passed. The disposable checkout produced `Cratebug.exe` and `Cratebug-amd64-installer.exe`, then was removed.

## Scope audit

The repository contains only the minimal Wails application shell, frontend-to-Go connectivity binding, validation, CI, and documentation.

Phase 0 did not introduce:

- Mod discovery or mutation logic
- Filesystem access to a Marvel Rivals mod directory
- Settings, metadata, or other persistence
- UAssetToolRivals integration
- BentoMod frontend code or state migration
- Release publishing or automatic updates

## Limitations and deferred work

- The executable and installer are unsigned.
- Signing, upgrade migration, release branding, versioned releases, and publishing are deferred.
- The ignored `build` directory is regenerated by Wails, so clean checkouts use Wails' default generated packaging assets.
- Cosmetic Windows Properties metadata is not embedded in `Cratebug.exe`.
- Installer lifecycle verification used the current Windows host and a disposable directory, not separate clean Windows 10 and Windows 11 virtual machines.
- Microsoft WebView2 Runtime remains a runtime prerequisite.
- Cratebug intentionally has no mod-management behavior yet.
